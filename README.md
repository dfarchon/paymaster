# Paymaster

`@dfarchon/paymaster` is an Aztec 6 project-sponsored fee
paymaster. It pays transaction fees from the Fee Juice balance held by its own
FPC address and restricts sponsored calls to an immutable list of target
contracts and account classes.

It deliberately has no per-user, per-day, seat, or transaction-count quota. The
FPC's Fee Juice balance is the sponsorship budget.

## Origin and thanks

This project started from [Alejo Amiras's quota-paymaster](https://github.com/alejoamiras/ecosystem-tooling/tree/main/packages/quota-paymaster).
Thank you to Alejo for the original paymaster design and implementation. This
repository keeps that foundation while adapting it for Aztec 6 and project
deployment, removing quota/seat logic, adding target and account-class
allowlisting, and providing a reusable browser/server SDK, funding helpers, and
deployment CLI.

## Packages

- `@dfarchon/paymaster`: contract artifact, SDK, funding helpers,
  and deployment utilities.
- `paymaster`: deployment CLI.
- `paymaster-fund`: L1 deposit and L2 claim CLI.
- `contracts/sponsored_fpc`: Noir FPC contract.

Aztec CLI `6.0.0` and Node `24.22.1` are required.

## Complete integration example

The following example assumes an application contract called `ExampleApp` and
an initializerless Schnorr account class.

### 1. Install the SDK

```sh
pnpm add github:dfarchon/paymaster#<commit>
```

Pin a commit in production so the deployed artifact and SDK cannot drift.

### 2. Configure the FPC

Copy `config/example.json` to `config/example-app.json` and replace the
environment references:

```json
{
  "name": "example-app",
  "maxFeeWei": "25000000000000000000",
  "allowedTargets": [
    { "name": "ExampleApp", "address": "env:EXAMPLE_APP_ADDRESS" }
  ],
  "allowedAccountClasses": [
    {
      "name": "SchnorrInitializerlessAccount",
      "classId": "0x<account-class-id>"
    }
  ],
  "requireUnpublishedAccounts": true
}
```

The target allowlist is contract-address based. Every method on an allowed
target is eligible, provided the call does not hide the user's sender. The SDK
exposes `isContractSupported()` to query this allowlist.

### 3. Deploy the FPC

The deployment CLI does not create an Aztec wallet. Create a context module in
your application that opens your Aztec 6 wallet and returns the deployer
address:

```ts
export default async function createContext() {
  return { wallet, deployer, sendOptions };
}
```

Deploy with:

```sh
pnpm exec paymaster deploy \
  --config ./config/example-app.json \
  --context ./deploy-context.ts
```

The path passed to `--context` must exist. `counter-deploy-context.ts` and
`funding-context.ts` are application files, not files generated by this
package. If you use the official `aztec-wallet` CLI for deployment, you can
deploy the compiled artifact directly with
`--payment method=fpc-sponsored,fpc=contracts:SponsoredFPC`; the custom CLI is
intended for applications that already have a JavaScript wallet context.

The CLI prints `SPONSORED_FPC_CONTRACT_ADDRESS`. Save that Aztec address; it is
the recipient to fund and the address the frontend must configure.

### 4. Fund the Paymaster

#### Testnet faucet (no `$AZTEC` required)

On testnet, the recommended bootstrap path is the
[Nethermind Aztec Faucet](https://aztec-faucet.nethermind.io). Select
`Testnet`, paste the Paymaster Aztec address, and request `Fee Juice`. The
faucet submits the L1 portal transaction and provides the claim flow. Wait for
the message to be relayed, then check the balance:

```sh
aztec-wallet \
  --node-url https://aztec-testnet.drpc.org \
  get-fee-juice-balance \
  <SPONSORED_FPC_AZTEC_ADDRESS> \
  --exact
```

The faucet gives Fee Juice, not the L1 `$AZTEC` token. Rate limits and
eligibility are controlled by the faucet service. If it does not accept a
contract address, use the L1 bridge path below; Fee Juice cannot be transferred
between L2 addresses.

#### L1 portal deposit (requires `$AZTEC` and Sepolia ETH)

The FPC does not bridge or claim funds by itself. The project operator supplies
a funding context containing an L1 wallet client and an Aztec operator wallet:

```sh
pnpm exec paymaster-fund deposit \
  --context ./funding-context.ts \
  --recipient <SPONSORED_FPC_AZTEC_ADDRESS> \
  --amount 100 \
  --output ./fpc-claim.json
```

`--amount` is in the L1 fee token's human-readable 18-decimal units. The
command uses `L1FeeJuicePortalManager.bridgeTokensPublic`, which performs the
L1 approval and deposit. The L1 wallet needs both `$AZTEC` and ETH for L1 gas.
Keep `fpc-claim.json` private until the claim succeeds; it contains the claim
secret.

The official wallet has an equivalent one-command bridge helper, but it still
requires `$AZTEC`:

```sh
aztec-wallet \
  --node-url https://aztec-testnet.drpc.org \
  bridge-fee-juice \
  100000000000000000000 \
  <SPONSORED_FPC_AZTEC_ADDRESS> \
  --l1-rpc-urls <SEPOLIA_RPC_URL> \
  --l1-chain-id 11155111 \
  --l1-private-key "$L1_PRIVATE_KEY"
```

### 5. Claim on Aztec L2

After the L1→L2 message is included, use the operator wallet in the same
funding context:

```sh
pnpm exec paymaster-fund claim \
  --context ./funding-context.ts \
  --claim-file ./fpc-claim.json
```

The operator account pays the claim transaction fee. The resulting Fee Juice is
credited to the FPC recipient, not the operator account. A claim can be
submitted by any party holding the secret, but each deposit can only be claimed
once.

### 6. Configure and use it in the frontend

```sh
VITE_SPONSOR_MODE=true
VITE_SPONSORED_FPC_ADDRESS=0x<deployed-fpc-address>
```

```ts
const fpc = new SponsoredFpcClient({
  node,
  wallet,
  address: import.meta.env.VITE_SPONSORED_FPC_ADDRESS,
  gasProfile,
  nodeUrl: import.meta.env.VITE_AZTEC_NODE_URL,
});

await fpc.register();
const supported = await fpc.isContractSupported(exampleApp.address);
if (!supported) throw new Error("ExampleApp is not sponsored");
await fpc.sendMethod({
  contract: exampleApp,
  method: "increment",
  args: [1n],
  player: accountAddress,
});
```

The SDK builds the account payload, authorization witness, fee settings, proof,
and broadcast. The frontend never needs to call `sponsor_and_execute` directly.

## Funding library

```ts
import { claimFeeJuice, depositFeeJuice } from "@dfarchon/paymaster";
```

`depositFeeJuice` returns the claim secret, amount, message hash, and leaf
index. `claimFeeJuice` submits `FeeJuice.claim` from the operator wallet and
credits the fixed FPC address.

## Contract support query

```ts
const supported = await fpc.isContractSupported(targetAddress);
```

The current on-chain policy is target-level, not function-selector-level. The
query returns false for a non-allowlisted target. It does not perform
function-selector-level checks.

## Testnet checklist

1. Set `NODE_URL=https://aztec-testnet.drpc.org` and use the Aztec 6.0.0 CLI.
2. Register the official testnet Sponsored FPC and bootstrap an operator account.
3. Deploy Counter (or your application contract) using the official Sponsored
   FPC for the deployment fee.
4. Deploy this Paymaster with the application address and account class in the
   immutable configuration.
5. Fund the Paymaster using the testnet faucet, or bridge `$AZTEC` from Sepolia
   and claim the L1→L2 message.
6. Verify the Paymaster's Fee Juice balance before testing a sponsored call.
7. In the frontend, instantiate `SponsoredFpcClient` and send the application
   method through `sendMethod`; do not call `sponsor_and_execute` directly.

The operator's L1 private key and Aztec wallet keys must stay in local
environment variables or a secret manager. Never commit them to the repository.

## Local Claim UI

After an L1 deposit, a claimer does not need to be the depositor. Anyone who
holds the one-time claim secret can submit the claim; the Fee Juice is credited
to the fixed Paymaster recipient. To run the local UI, point it at a funding
context that contains an Aztec wallet and claimer account, or create a local
ephemeral claimer from the page:

```sh
pnpm claim-ui
```

Open `http://127.0.0.1:8787`, click **Create local Aztec claimer account**, and
save the displayed account backup values. Then enter the `claimAmount`,
`claimSecret`, and `messageLeafIndex` printed by the L1 deposit and submit. The
account is an ephemeral initializerless account held by the local server; the
page registers Aztec's official testnet Sponsored FPC (salt `0`) and uses it to
pay the claim transaction, so this account does not need an existing Fee Juice
balance. The bridged Fee Juice is still credited to the fixed Paymaster
recipient. The page does not use or expose the L1 private key. To reuse an existing operator
wallet instead, set `PAYMASTER_FUNDING_CONTEXT=./funding-context.ts` before
starting. The server binds only to
loopback and does not log claim secrets. Do not expose this endpoint to the
public internet; a claim secret is a bearer credential.

## Testnet Counter example

The repository includes a minimal Aztec 6 Counter contract and a public-testnet
runbook in [`examples/counter`](./examples/counter). It shows the complete
sequence: bootstrap an operator with the official testnet Sponsored FPC,
deploy Counter, deploy this project Paymaster with Counter allowlisted, bridge
Fee Juice from Sepolia, claim it to the Paymaster, and send `increment()` via
`SponsoredFpcClient`.

Aztec testnet currently runs on Ethereum Sepolia and exposes
`https://aztec-testnet.drpc.org`. See the [official testnet guide](https://docs.aztec.network/developers/getting_started_on_testnet)
and [network list](https://docs.aztec.network/networks) for current endpoints
and version requirements.
